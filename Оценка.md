## Веб-приложение строительной компании с конфигуратором дома и калькулятором ремонта

**Дата оценки:** 20 октября 2026 г.  
**Срок завершения проекта:** 10.10.2026 (21 день)  
**Руководитель проекта:** Гаршин Владислав

## 1. Общая характеристика проекта

Проект относится к категории **«сборка из известных решений в сжатые сроки»**. Типовое веб-приложение на стандартном стеке (Java 17, Spring Boot, PostgreSQL, Vite) с десятью функциональными модулями, объединёнными в единую систему.

**Ключевые параметры:**
- Длительность: 21 день (3 итерации по 7 дней + итерация 0)
- Команда: PM/BA, Frontend, Backend, QA/контент
- Методология: гибридная
- Жёсткие ограничения: срок, состав команды, демо-характер расчётов

## 2. Оценка сроков

### 2.1. Оценка по трём точкам (PERT)

Для фазы активной разработки (итерации 1–3, суммарно 21 день) проведена трёхточечная оценка:

| Сценарий | Длительность | Обоснование |
| :--- | :---: | :--- |
| **O (оптимистичный)** | 15 дней | Контент предоставлен в срок, правила расчёта согласованы на итерации 0, интеграция Frontend/Backend без ошибок |
| **M (наиболее вероятный)** | 21 день | Плановый срок по Уставу, с учётом частичной занятости учебной команды |
| **P (пессимистичный)** | 30 дней | Изменение логики конфигуратора на 2-й неделе, задержка контента, рефакторинг Backend из-за ошибок расчёта |

**Расчёт ожидаемой длительности и стандартного отклонения:**

- Ожидаемая длительность (E) = (P + 4 * M + O) / 6 = (30 + 4 * 21 + 15) / 6 = 129 / 6 = **21,5 дня**
- Стандартное отклонение (SD) = (P - O) / 6 = (30 - 15) / 6 = 15 / 6 = **2,5 дня**

**Интерпретация:**
- С вероятностью ~68% (E + 1 * SD) разработка займёт **24 дня**, что превышает жёсткий дедлайн 21 день.
- С вероятностью ~95% (E + 2 * SD) разработка займёт **26,5 дней**.

### 2.2. Метод критической цепи

Поскольку ожидаемая длительность (21,5 дня) уже превышает плановый срок, применение индивидуальных буферов к каждой задаче приведёт к гарантированному срыву дедлайна. Рекомендуется:

1. Оценивать задачи внутри итераций **агрессивно** — без индивидуальных буферов, по реалистичному сценарию.
2. Сэкономленное время собрать в **единый буфер проекта** (3–4 дня) в конце 3-й недели.
3. Управлять буфером как ресурсом: ежедневно отслеживать его расход.
4. При начале расходования буфера — немедленно урезать содержание (отключить отзывы, FAQ, расширенную админку), сохраняя ядро: конфигуратор, калькулятор, форма заявки, PDF-смета, базовая админка.

### 2.3. Оптимизация времени ожидания

Доля времени, когда над задачей действительно работают, обычно составляет 5–20%. Остальное — ожидание (ревью, ответ заказчика, освобождение ресурса, деплой). В учебной команде это усугубляется расписанием.

**Действия:**
- Не планировать задачи, требующие синхронной работы двух человек, без предварительной брони времени.
- Использовать асинхронную коммуникацию: задачи в трекере, комментарии к PR, контракт API как точка синхронизации.

### 3.3. Совокупная стоимость владения (TCO) для реального заказчика

После передачи проекта в эксплуатацию «СтройСервис» столкнётся со следующими затратами, не учтёнными в бюджете разработки:

1. **Инфраструктура:** VPS для Java-приложения, PostgreSQL, Docker-контейнеры, SSL-сертификат, резервное копирование. Значительно дороже статического хостинга.
2. **Поддержка логики расчётов:** цены на материалы и работы меняются. Требуется время менеджера или разработчика на обновление справочников в админке.
3. **Юридическое сопровождение:** сбор контактных данных в форме заявки требует соблюдения 152-ФЗ (политика конфиденциальности, отдельное согласие, уведомление в Роскомнадзор).
4. **Лицензионная чистота:** при использовании библиотек для генерации PDF (например, iText с лицензией AGPL) необходимо либо выбрать альтернативу с MIT/Apache, либо заложить бюджет на коммерческую лицензию.
5. **Реакция на инциденты:** падение сайта, уязвимости, обновления безопасности Spring Boot.

## 4. Факторы, влияющие на длительность и качество

### 4.1. Ошибка планирования

Команда склонна оценивать «счастливый путь». Необходимо применить **взгляд снаружи**: взять статистику прошлых учебных проектов аналогичного объёма. Если медиана подобных проектов составляет 25–28 дней, базовую оценку в 21 день нужно искусственно сжать до 17 дней чистой работы, оставив 4 дня на непредвиденные обстоятельства.

### 4.2. Влияние LLM на проект

| Тип работы | Делегируемо LLM? | Обоснование |
| :--- | :---: | :--- |
| Парсинг даты, валидация телефона | Да, полностью | Проверка дешевле производства (тест за секунды) |
| Генерация 20 строк JSON для каталога | Да, полностью | Тривиальная задача, мгновенная проверка |
| Boilerplate CRUD в админке | Да, полностью | Типовой код, проверяется тестами |
| Проектирование структуры БД для конфигуратора | Нет | Ошибка обнаружится через неделю, стоит переписывания |
| Выбор библиотеки для PDF | Частично | Модель даст критерии, но решение зависит от контекста проекта |
| Оценка сроков модуля | Нет | Модель выдаст правдоподобное, но нерелевантное команде число |

**Правила безопасности:**
- Запрет на отправку реальных или правдоподобных персональных данных (из тестовых заявок) в промпты внешних LLM.
- Автоматическая проверка лицензий в CI для сгенерированного кода.
- Обязательное объяснение автором любого сложного или сгенерированного участка кода на ревью.

### 4.3. Специфика строительной предметной области

- **Сложная структура каталога:** проекты домов имеют множество параметров (площадь, этажность, материал стен, тип фундамента). Необходимо продумать модель данных заранее.
- **Пошаговый конфигуратор:** состояние должно сохраняться между шагами, пересчёт стоимости — мгновенный. Требует продуманного UX и производительного Backend.
- **PDF-смета:** должна содержать обязательные поля (объёмы, материалы) согласно требованиям Госстройнадзора. Кириллица и форматирование — критичны.
- **Демо-характер расчётов:** необходимо явно маркировать смету как предварительную, чтобы избежать юридических рисков.

## 5. Резюме для руководителя проекта

Для успешной сдачи проекта «СтройСервис» в срок 21 день рекомендуется:

1. **Жёсткая приоритизация (MoSCoW):**  
   - *Must have:* каталог проектов, конфигуратор дома, калькулятор ремонта, форма заявки, PDF-смета, базовая админка.  
   - *Should have:* главная страница, каталог услуг, FAQ.  
   - *Could have:* отзывы, портфолио «до/после», расширенная админка (делаются только при наличии времени в буфере).

2. **API First:** Заставить Backend (Никитин И.) и Frontend (Белицкая У.) согласовать JSON-контракты до начала написания кода. Это устранит главный риск интеграции.

3. **Изоляция сложности:** Движок расчёта стоимости должен быть максимально изолирован. Получить от заказчика 3–5 конкретных примеров расчёта «на бумаге» и превратить их в автотесты на Backend **до** начала разработки UI конфигуратора.

4. **Управление буфером:** Не размазывать резерв времени по задачам. Объявить команде дедлайн «готовности функционала» на 18-й день. Оставшиеся 3 дня — священный буфер проекта на исправление дефектов, генерацию PDF и финальную сборку документации.

5. **Контроль качества кода:** Ввести обязательное правило: разработчик должен устно объяснить логику любого сгенерированного ИИ или сложного участка кода на ревью. Если не может объяснить — код не принимается (защита от технического долга).

6. **Управление контентом:** Установить жёсткий дедлайн передачи контента от заказчика — 14-й день. При неподаче — сдавать проект с демо-данными, подготовленными командой на основе легенды.

7. **Документация параллельно разработке:** Не откладывать написание инструкций и спецификаций на последнюю неделю. Тестировать по ходу итераций, документировать по мере готовности модулей.

---

**Заключение:** Проект выполним в срок 21 день при условии жёсткой приоритизации содержания, применения метода критической цепи, ранней синхронизации API и изоляции движка расчётов. Основные риски — изменение требований и ошибки в логике расчёта — управляются через фиксацию границ в Уставе, еженедельные демо и автотесты на бизнес-правила.
